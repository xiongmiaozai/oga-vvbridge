# 纹理文件通道与格式详解（textures/blocks/ 六类文件）

> 整理日期：2026-11-15
> 对象：`textures/blocks/` 下 `iron_block.png` / `iron_block.texture_set.json` / `iron_block_mer.png` / `iron_block_mers.tga` / `iron_block_normal.tga` / `iron_block_heightmap.tga` 这 6 类文件的**通道定义、格式、命名与注意事项**
> 依据：Microsoft Learn《Texture Set JSON and Introduction to Texture Sets》[1]、《Overview of Physically Based Rendering》[2]、MineGraph《MERS 材质标准》[3]、本地 `04`/`05`/`02`/`12` 号资料，以及 **Mojang 官方样例包实物** `bedrock-samples-v1.26.70.23-preview-full.zip`（23,037 个文件）[4]
> 方法：网页通道取规范原文；实物流直接解析 ZIP 内的 JSON 正文与 TGA / PNG 二进制头及像素，用于校验或推翻文档说法

## 一、先纠正一个前提：这 6 个文件不是「一套」

这棵树是 `11_文件与文件夹命名全表.md` 第 229–234 行的**示意树**，它画的是「可选层菜单」，不是某个真实方块目录下同时存在的 6 个文件。两处硬约束：

| 互斥对 | 约束来源 | 说明 |
|---|---|---|
| `metalness_emissive_roughness`（MER） ⊕ `metalness_emissive_roughness_subsurface`（MERS） | Texture Set schema [1] | 同一个 `texture_set.json` 里**不能同时声明**两个字段，否则 `CONTENT_ERROR`，整个纹理集不生效 |
| `normal` ⊕ `heightmap` | Texture Set schema [1] | 同上，二选一 |

注意区分：**文件本身可以同时躺在目录里**，错的只是 JSON 里同时引用。但引擎按 `.tga > .png > .jpg > .jpeg` 优先级找图 [1]，多余文件纯属浪费体积。

**官方原版包里 `iron_block` 实际只有 3 个文件**（实物核验 [4]）：

```
resource_pack/textures/blocks/
├── iron_block.png                 16×16, PNG, 8-bit RGBA
├── iron_block.texture_set.json     format_version "1.21.30"
└── iron_block_mers.tga            16×16, 32-bit BGRA TGA
```

`iron_block_mer.png` 来自 **MS Learn 的「做一面镜子」教程**（RTX 时代遗留，用 `format_version: "1.16.100"` + MER + `capabilities: ["pbr","raytraced"]`）[2]；`iron_block_normal.tga` / `_heightmap.tga` 是规范允许的可选层，官方包里前者只在 4 个水/岩浆流体纹理集上用到、后者 **0 个** [4]。

> 结论：做灵动视效（VV）包时，按「最小三件套」出图即可；`_mer.png` 属于旧 RTX 写法，`_heightmap` 实际已边缘化。详见第九节。

## 二、`iron_block.png` — 基色 / color 层

| 项 | 内容 |
|---|---|
| **通道** | RGB 3 通道（Alpha 默认统一 1.0）或 RGBA 4 通道；R/G/B = 可见颜色，A = 透明度 [1] |
| **必需性** | **唯一必需层**。缺 `color` 的纹理集直接判为无效 [1] |
| **格式** | 支持 `.tga` / `.png` / `.jpg` / `.jpeg`，优先级 `.tga > .png > .jpg > .jpeg` [1]；官方用 **PNG，8-bit，color type 6 = RGBA**，`16×16` [4] |
| **命名** | 无后缀，且必须与 `.texture_set.json` 同名同目录；JSON 里引用**不带扩展名** |
| **注意** | ① 这是经典（非 PBR）管线**唯一**会读的层 [1]；② 官方说基色图里「通常烘焙了光照」[1]；③ 官方 `iron_block.png` 是 RGBA，若自制基色图带透明通道，VV 下会按透明处理；④ 只能引用**同一个资源包内**的贴图，高优先级包的同名图不会覆盖本包 texture_set 的引用 [1] |

## 三、`iron_block.texture_set.json` — 纹理集定义

### 3.1 官方实物写法（可直接抄）

`resource_pack/textures/blocks/iron_block.texture_set.json` 全文 [4]：

```json
{
    "format_version": "1.21.30",
    "minecraft:texture_set": {
        "color": "iron_block",
        "metalness_emissive_roughness_subsurface": "iron_block_mers"
    }
}
```

对照 MS Learn 教程里的旧写法 [2]：

```json
{
  "format_version": "1.16.100",                  // 旧：RTX / MER 时代
  "minecraft:texture_set": {
    "color": "iron_block",
    "metalness_emissive_roughness": "iron_block_mer"   // 旧：三通道 MER
  }
}
```

**`format_version` 规则**：MER 用 `"1.16.100"`，**一旦用 MERS 就必须 `≥ "1.21.30"`** [5]。官方包 3,171 个纹理集全部是字符串 `"1.21.30"`，无一例外 [4]。它是 schema 引入版本，不是游戏版本（1.26.70 的包仍写 1.21.30，见 `12_` 号报告第四节）。

### 3.2 完整 schema（1.21.30）[1]

| 字段 | 值类型 | 对应层 | 通道 |
|---|---|---|---|
| `color` | 短名字符串 / 4 值数组 / hex | 基色 | RGB 或 RGBA |
| `normal` | 短名字符串 | 法线 | RGB（4 通道时 A 忽略） |
| `heightmap` | 短名字符串 / 单值 | 高度 | 1 通道灰度 |
| `metalness_emissive_roughness` | 短名字符串 / 3 值数组 / hex | MER | RGB（4 通道时 A 忽略） |
| `metalness_emissive_roughness_subsurface` | 短名字符串 / 4 值数组 / hex | MERS | **必须 RGBA** |

字段值的三种写法可**混用** [1]：

- 贴图短名字符串（不带扩展名）：`"color": "iron_block"`
- 0–255 整数或数组：`"metalness_emissive_roughness_subsurface": [255, 0, 64, 0]`
- 十六进制：`"color": [180, 140, 190, 255]`、`"metalness_emissive_roughness": "#FBA34C"`；3/4 通道用 RGB/ARGB，单通道用 2 位 hex

> ⚠️ **uniform 值的坑**：官方明确警告「纹理变体（texture variations）中使用 MERS 的 uniform 值不受支持，必须提供基于图片的 MERS 文件才能正确生效」[1]。也就是说 `terrain_texture.json` 里做 variants 时，别指望用数组糊过去。

### 3.3 无效条件（触发 `CONTENT_ERROR`，整个纹理集不生效）[1]

- JSON 无法解析或不符合 schema
- **没有 `color` 层**
- 同时定义 `heightmap` 与 `normal`
- 对 item 等「基于纹理的对象」使用 `heightmap`（VV 中禁用，应改用 normal）
- 同时定义 MER 与 MERS
- 引用的贴图在同包内不存在，或无法解析
- 通道数不符：引用图片时 Color / MER / Normal 支持 3 或 4 通道，**MERS 只支持 4 通道**，heightmap 只支持 1 通道；用数值/hex 时 Color 需 4 值、MER 3 值、MERS 4 值

### 3.4 资源栈行为 [1]

- 只能引用**同一资源包**内的图片
- 高优先级资源包里的贴图**不会**覆盖本包 texture_set 的引用
- 同名 texture_set 在包栈中**不合并**，高优先级包的定义整份替换低优先级的

## 四、`iron_block_mer.png` — MER 三通道（RTX / 旧式）

| 项 | 内容 |
|---|---|
| **通道** | R = 金属度 Metalness、G = 自发光 Emissive、B = 粗糙度 Roughness；A 若存在则**被忽略** [1] |
| **数值** | 各通道 0–255 ↔ 0.0–1.0；金属度黑=非金属 / 白=纯金属，粗糙度黑=极光滑 / 白=极粗糙，自发光黑=不发光 / 白=最亮 [2] |
| **格式** | 3 通道（或 4 通道忽略 A）图片；MS Learn 教程给的是 **PNG** [2] |
| **适用** | RTX 光追模式；**VV 也兼容该字段**，但不支持 SSS [1]。官方原版包 **0 个** `_mer.*` 文件 [4] |
| **注意** | ① 与 MERS **互斥**，同一 JSON 不能同时写；② RTX 资源包**不会使用** `metalness_emissive_roughness_subsurface` 字段 [1]；③ 教程同时要求 `capabilities: ["pbr","raytraced"]` 和 `min_engine_version ≥ [1,21,120]`，做 VV 包只写 `"pbr"` 即可 [2] |

> 这条路径是 2020 年 RTX 时代留下的。做 1.26.x 的 VV 包，**不要**再输出 `_mer.png`。

## 五、`iron_block_mers.tga` — MERS 四通道（VV 推荐，实测唯一答案）

### 5.1 通道定义

| 通道 | 属性 | 0 | 255 |
|---|---|---|---|
| **R** | 金属度 Metalness | 非金属 | 金属 |
| **G** | 自发光 Emissive | 不发光 | 最大发光 |
| **B** | 粗糙度 Roughness | 完全光滑 | 完全粗糙 |
| **A** | 次表面散射 Subsurface | 无散射 | 最大散射 |

来源：MineGraph 中文标准 [3]、MS Learn [1][2]、Minecraft Wiki [6]。

**金属度与 SSS 互斥规则**（很容易漏）[1][3]：

- 两者**不能同时生效**，游戏取 `max(metalness, subsurface)` 决定主属性；**相等时优先 SSS**
- 只有非金属能有次表面散射
- 例：`[64, 0, 0, 128]` → 非金属 + SSS=128；`[255, 0, 0, 64]` → 金属 + SSS=0
- 官方建议金属度当**二值**（0 或 255）用，中间值虽允许但不物理准确，可用于特殊风格 [1]

### 5.2 为什么必须 TGA

MineGraph 原文 [3]：

> Alpha 通道的次表面散射强度在值为 **0 与 255 时仍然按预期工作**，因此大多数弱次表面散射物体的 PBR 纹理在资源管理器里预览起来是透明的。而 Photoshop 等工具对 **PNG 的优化会导致 Alpha=0 区域丢失 RGB 数据**，因此**只能使用 TGA 格式**。

官方实物完全印证：3,171 个 `_mers` **100% 是 `.tga`**，无一个 PNG/JPG [4]。

### 5.3 TGA 二进制实测（转换器的关键，之前 12 号报告没覆盖）

解析 3,171 个 `_mers.tga` 的 18 字节 TGA 头 [4]：

| 指标 | 实测 |
|---|---|
| 位深 | **32-bit：2,885 个**（`alpha_bits=8`）；**24-bit：286 个**（`alpha_bits=0`） |
| image type | 2 = 未压缩真彩色 |
| 原点 | `y_top=False`，即**左下角原点**（TGA 标准）；**但有 23 个例外**是 `descriptor=40`（上左原点），详见文末附录 A |
| 字节序 | **BGRA**，不是 RGBA |

像素级验证 `iron_block_mers.tga`（16×16，按 BGRA 解出 R/G/B/A 均值）：

```
R(金属度)=191.0   G(自发光)=0.0   B(粗糙度)=136.7   A(SSS)=0.0
前 3 像素：(191, 0, 176, 0) ...
```

对铁块而言「金属度高、不发光、中等粗糙、无散射」完全合理；若误按 RGBA 解读会变成 `R=0 / G=137 / B=191 / A=0`（非金属却自发光），物理上不成立 —— **反证了 TGA 是 BGRA**。`raw_iron_block_mers.tga` 为 `(128, 0, 160.7, 0)`，同样吻合。

> ⚠️ **实物与规范文字存在张力**：规范说「MERS 只支持 4 通道图」[1]，但官方包里有 **286 个 24-bit（无 alpha）MERS**，分布在 `blocks` 132 / `items` 86 / `entity` 64 / `particle` 2 / `trims` 2，且全部仍被 MERS 字段引用。抽样这些图（紫水晶、蓝冰、仙人掌）G 通道全为 0，即无自发光、无 SSS 的材质。说明引擎对缺 alpha 有容错（大概率按 SSS=0 处理），但**规范未明文允许**。给转换器的建议：统一输出 **32-bit BGRA TGA**，别赌容错。

**PNG → TGA 不能只改扩展名**，必须做两件事：

1. 通道重排 `RGBA → BGRA`；
2. 行序翻转（PNG 左上原点 → TGA 左下原点）。

最小可用写出代码：

```python
from PIL import Image                      # pip install pillow
im = Image.open("iron_block_mers.png").convert("RGBA")
r, g, b, a = im.split()
bgra = Image.merge("RGBA", (b, g, r, a))   # 通道重排
bgra = bgra.transpose(Image.FLIP_TOP_BOTTOM)  # 原点翻转
bgra.save("iron_block_mers.tga", format="TGA")
# 校验：读出头应为 depth=32, descriptor alpha_bits=8, y_top=0
```

### 5.4 命名与配对

`<name>_mers.tga` 必须与 `<name>.texture_set.json`、`<name>.png` **同目录同名**；官方 3,171 组严格 1:1 [4]。JSON 里写 `"iron_block_mers"`，**不带 `.tga`** [1]。

## 六、`iron_block_normal.tga` — 法线层

| 项 | 内容 |
|---|---|
| **通道** | RGB = 切线空间法线的 X / Y / Z；**平面值 (128, 128, 255)** [2]。4 通道时 A 被忽略 [1] |
| **格式** | 3 或 4 通道图；扩展名按通用优先级。官方这 4 个都是 `.tga` [4] |
| **互斥** | 与 `heightmap` 二选一；VV 中 **item 等基于纹理的对象只能用 normal，不能用 heightmap** [1] |
| **官方用量** | 全包 3,171 个纹理集中**只有 4 个**引用 normal 层：`water_still_grey`、`water_flow_grey`、`lava_still`、`lava_flow`（全是流体）[4] |

### 6.1 官方 normal 贴图的实际位深（有反直觉之处）[4]

| 文件 | 尺寸 | 位深 / type | 像素均值 |
|---|---|---|---|
| `lava_flow_normal.tga` | 32×512 | 24-bit, type=2 | `(127.4, 127.4, 252.9)` ≈ 平面值 (128,128,255) |
| `lava_still_normal.tga` | 16×512 | 24-bit, type=2 | `(127.4, 127.4, 254.8)` |
| `water_flow_grey_normal.tga` | 32×1024 | **8-bit, type=1（带调色板的索引 TGA）** | 需读 colormap，按真彩解析会失败 |
| `water_still_grey_normal.tga` | 16×512 | 8-bit, type=1 | 同上 |

尺寸 `16×512` / `32×1024` 是**动画帧纵向排列**（每帧正方形），与动画纹理约定一致。

### 6.2 ⚠️ 命名陷阱：文件名带 `_normal` 不等于法线贴图

官方包里有大量 `piston_top_normal.png`、`rail_normal.png`、`book_normal.png`、以及 chest 目录下干脆叫 `normal.png` 的文件 —— 它们**全是基色贴图**，各自配 `_mers.tga`，其 texture_set 里写的是 [4]：

```json
{ "color": "piston_top_normal",
  "metalness_emissive_roughness_subsurface": "piston_top_normal_mers" }
```

即 `"color"` 字段的值恰好以 `_normal` 结尾。**后缀只是约定，真正决定某张图属于哪一层的是 `texture_set.json` 里的字段名**。统计时要解析 JSON 的 key，不能用字符串匹配 —— 用 `grep '"normal"'` 会得到 5 个，实际作为层字段的只有 4 个（`normal.texture_set.json` 里的是 `"color": "normal"` 被误命中）[4]。

### 6.3 法线 Y 朝向（上一轮标为「未定论」，本轮有了可用结论）

LabPBR 的 `_n` 明确是 **DirectX / Y-**，且 B 通道存 AO、A 通道存高度图 [7]。基岩侧查到两条独立实现证据：

- `jasonjgardner/comfy-ui-minecraft-pbr` 的 *Pack Bedrock RTX* 节点：`flip_normal_y` **默认 true**，注释写明 *"Bedrock expects DirectX Y-down; flips an OpenGL Y-up normal. Disable only if your input is already DirectX."*，并强调 Bedrock 法线是 **RGB only，不打包 AO 或高度** [8]
- `jasonjgardner/minecraft-pbr-converter`（TS 双向转换器 README）：Bedrock 侧输出 *"a DirectX normal (RGB only - Bedrock doesn't pack AO or height)"* [9]

**结论**：基岩 / VV 用 **DirectX (Y-)**，与 LabPBR `_n` 同向 —— 因此 **LabPBR → VV 时不需要翻转 G 通道**；若源是 OpenGL (Y+) 法线才需要翻转。但要拆掉 LabPBR `_n` 里的 B=AO、A=高度：VV 的 normal 只吃 RGB 法线，AO 得烘进基色或丢弃，高度可另存 `_heightmap`。

> 来源等级提示：以上两条是**第三方转换器实现**，不是 Mojang 官方明文。MS Learn 只给了 (128,128,255) 平面值 [2]，未声明 Y 朝向。建议转换器提供 `flip_normal_y` 开关，并在游戏内用斜射光看一次凹凸方向做最终确认。

## 七、`iron_block_heightmap.tga` — 高度图层

| 项 | 内容 |
|---|---|
| **通道** | **1 通道灰度**，或 JSON 里写单个数值作统一高度 [1] |
| **数值** | 黑(0.0) = 最大内凹；`(127,127,127)` ≈ 0.5 = 不凹不凸；白(1.0) = 最大外凸 [2] |
| **互斥** | 与 `normal` 二选一；**VV 中不能用于 item 等基于纹理的对象** [1] |
| **效率** | 官方称它是 normal 的替代方案，但**效率更低、可表达的纹理更少** [2] |
| **官方用量** | **0 个** heightmap 文件、0 个纹理集引用 [4]（包里唯一的 `minecraft_overworld_height.json` 与此无关） |

> 在 VV 时代基本可视为废弃路径：规范保留、RTX 教程用过（`grass_carried_heightmap` 示例 [1]），但原版 1.26.70 完全不用。转换器优先级最低。

## 八、`pbr/global.json` — 缺省值回退（补上 10/11 号文档的空白）

当纹理集缺某一层，或自定义纹理**根本没有** texture_set 时，默认值由它决定 [10][11]：

```json
{
  "format_version": "1.21.40",
  "minecraft:pbr_fallback_settings": {
    "blocks":    { "global_metalness_emissive_roughness_subsurface": [0, 0, 255, 0] },
    "actors":    { "global_metalness_emissive_roughness_subsurface": [0, 0, 255, 0] },
    "particles": { "global_metalness_emissive_roughness_subsurface": [0, 0, 255, 0] },
    "items":     { "global_metalness_emissive_roughness_subsurface": [0, 0, 255, 0] }
  }
}
```

- 根 schema `minecraft:pbr_fallback_settings`，`format_version` 需 `"1.21.40"`；四类对象 `blocks` / `actors` / `particles` / `items` 结构相同 [10][11]
- 字段名 `global_metalness_emissive_roughness_subsurface`（MERS）或 `global_metalness_emissive_roughness`（MER），值支持 RGBA 数组或 HEX 字符串 [11]
- 规则：替换原版纹理而缺某层时**回退到原版贴图**；附加的自定义纹理若无纹理集，则所有像素取这里的 MERS 默认值 [10]
- **官方样例包里 `pbr/` 目录不存在、0 个 `pbr_fallback_settings`** [4] —— 因为原版自带全部 3,171 个纹理集，不需要回退。这是**第三方包才需要**的文件，10/11 号文档把它列入「九大目录」属于创作者可选扩展，与实物一致

另需注意 MS Learn [2] 的通用规则：*Not all PBR texture sets require all maps. Leaving empty maps will cause the texture set to use the default value.*

## 九、三处「文档 vs 实物」矛盾（本轮新发现）

| # | 文档说法 | 实物 / 检索结果 | 处理建议 |
|---|---|---|---|
| 1 | [1]「MERS 只支持 4 通道图」，缺通道会 `CONTENT_ERROR` | 官方 **286 个 24-bit（无 alpha）MERS** 仍被正常引用 [4] | 引擎有容错；转换器仍统一输出 **32-bit**，别赌 |
| 2 | 官方样例包自带 `documentation/Texture Sets.html` 应当是最权威的 schema | 该文件里 `metalness_emissive_roughness_subsurface` / `subsurface` / `MERS` / `1.21.30` **出现次数全为 0**，只有 `1.16.100` ×3 与 MER 字段 [4]；bedrock.dev 的 1.26.0 Texture Sets 文档同样只有 MER [12] | 包内文档是 **RTX 时代遗留模板**，没同步 VV 扩展；**以 MS Learn 网页版 + 实物为准**，别用包内 HTML 当 schema 源 |
| 3 | 11 号示意树把 6 个文件并列 | 官方 `iron_block` 只有 3 个；MER⊕MERS、normal⊕heightmap 互斥 | 示意树是菜单不是套装，已在 11 号加注并指向本文档 |

## 十、给转换器的直接指令（汇总）

| 环节 | 该做什么 | 别做什么 |
|---|---|---|
| 输出文件 | `<name>.png` + `<name>.texture_set.json` + `<name>_mers.tga` **三件套，同名同目录** | 别只出 `_mers.tga` 却漏 JSON |
| MERS 编码 | R=金属度、G=自发光、B=粗糙度、A=SSS；**32-bit BGRA TGA、左下原点** | 别把 PNG 改后缀当 TGA；别按 RGBA 写；别用 24-bit |
| texture_set.json | `format_version: "1.21.30"` + `color` + `metalness_emissive_roughness_subsurface`，值不带扩展名 | 别写 `1.16.100`、别写 MER、别同时写 normal+heightmap |
| manifest.json | 加 `capabilities: ["pbr"]`，`min_engine_version ≥ [1,21,120]` [2] | 别照抄官方样例包（它没写 capabilities）[4] |
| 通道换算 | LabPBR `_s` 的 R=感知平滑度 → MERS B 粗糙度需 `pow(1−s, 2)`；A=自发光 → MERS G | 别按通道直接搬运（见 `12_` 号报告第七节） |
| 法线 | DirectX (Y−) 与 LabPBR 同向，**不翻 G**；只保留 RGB，B=AO / A=高度要拆出或丢弃 [8][9] | 别把 LabPBR `_n` 整张当 VV normal 用 |
| 可选层 | normal / heightmap 优先级最低；VV 的 item 禁用 heightmap | 别生成 `textures_list.json`（官方包没有，非必需）[4] |
| 回退 | 若自定义纹理不逐个出 MERS，写 `pbr/global.json` 兜底 [10][11] | 别依赖「留空自动用原版」——那只适用于替换原版纹理 |

## 附录 A：第 16 号验证追加的实物补充（2026-11-15）

`16_端到端转换验证报告.md` 用 `verify/official_regression.py` 对官方包 3,171 组 MERS 做了全量二进制回归，本节结论均来自该脚本，**不是网页文档**。原有结论（BGRA / 32-bit 2,885 个 / 24-bit 286 个 / `iron_block` 首像素 `(191,0,176,0)` / 均值 `R=191.0, B=136.7`）全部复核通过，实测 `B=136.7421875`。追加四处此前未记录的细节：

**A.1 TGA 原点不统一。** `descriptor` 实测分布为 `8`: 2,862 个、`0`: 286 个、**`40`: 23 个**。`0x28 = 0b00101000` 表示 `alpha_bits=8` 且 `y_top=1`（**上左原点**），与另外 3,148 个的左下原点相反。这 23 个分布为 blocks 17 / items 5 / particle 1，集中在 `icicle_*`、`jukebox_*`、`polished_calcite_*`、`calcite_pillar_*`、`chiseled_soulshale`、`straw_bed_particle`、`music_disc_flurry` 等较新的方块与物品。

> 影响：本转换器自己按左下原点写出，不受影响；但**任何把官方 TGA 当输入解析的工具必须读 descriptor 判断行序**，不能写死 `y_top=False`。第九节「MERS 编码」那一行应理解为「我们输出时的约定」。

**A.2 MERS 字段可以写常量数组。** `resource_pack/textures/flame_atlas.texture_set.json` 是官方包里唯一一例：

```json
{
    "format_version": "1.21.30",
    "minecraft:texture_set": {
        "color": "flame_atlas",
        "metalness_emissive_roughness_subsurface": [0, 255, 255, 0]
    }
}
```

即 MERS 四通道可用常量 `[metalness, emissive, roughness, subsurface]` 直接给出，不必引用贴图。这是转换器目前未利用的能力：对于「整块材质均匀」的方块，比输出一张纯色 `_mers.tga` 更省；也可作为无 `_s` 时比 `pbr/global.json` 更精确的按纹理回退。

**A.3 一处跨目录冗余。** `textures/blocks/straw_bed_particle_mers.tga` 没有同目录的 `.texture_set.json`，其同名 texture_set 在 `textures/particle/`。属于官方包自身的散落文件，不是配对错误；按「同目录严格配对」写校验脚本会误报 1 例。除此之外 3,171 组严格 1:1，0 引用断裂、0 值带扩展名。

**A.4 连续金属度与互斥规则的真实语义。** 对 5,687,059 个 32-bit 像素统计：

| 现象 | 数量 | 含义 |
|---|---|---|
| 金属度取值在 `1..254` 之间 | 389,191（**6.84%**） | MERS 支持**连续金属度**（铁块均值 191）。LabPBR `_s` 的 G 通道只有「介电质 F0 / 硬编码金属」二值语义，转换只能输出 0 或 255 —— 规范级信息损失，非实现 bug |
| 金属度与 SSS **同时非零** | 41,589 | 「互斥」是**渲染时取较大值**的规则，不是数据约束；`02_` 号的表述正确，转换器相等时两者都保留与该规则一致 |

round-trip 回归（反解官方 MERS → 逆推 LabPBR `_s` → 再转回）显示：粗糙度与自发光误差为 0（8-bit 量化后仍 ≤1），金属度仅 93.34% 像素误差 ≤1，损失全部来自 A.4 的连续金属度。详见 `16_` 号报告 §3.4。
