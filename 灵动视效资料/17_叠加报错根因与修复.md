# 17 · 转换包与已有 PBR 包叠加时报「资源包加载错误」——根因与修复

> 实证日期：2026-11-15　|　对象：用户上传的**转换后成品包** `A Multi domain 1024x内测版本1.0.mcpack`（144 MB / 363 文件）
> 对照基准：`ENRO 0.20网易版2.mcpack`（38 MB / 1699 文件，用户确认可正常加载的商业 VV 包）
> 官方样例包：`bedrock-samples-v1.26.70.23-preview-full.zip`

---

## 一、用户实测现象

把**转换后的 `.mcpack`** 和 **ENRO 包**一起启用时，游戏提示「有 1 个资源包加载错误」。
此前几轮已经修过封面（游戏资源包列表里的 `pack_icon.png`）、名称自动识别等，但**加载报错**一直没定位到根因；
而且我前几轮给出过一个**错误猜测**（见 §五订正）。这次拿到了用户游戏里实际用的转换成品包，得以做全量文件级实证。

---

## 二、实证方法

把两个包都当 ZIP 解包，逐文件核对：manifest / UUID / 全部 JSON 合法性 / 全部 PNG 签名 / 全部 TGA 头 /
`texture_set.json` 悬空引用 / 文件名合法性 / 重复 ZIP 条目 / 两包同名路径交集。结果如下。

| 检查项 | 转换包（报错） | ENRO（正常基准） | 判定 |
|---|---|---|---|
| `manifest.json` | `format_version:2`、`capabilities:["pbr"]`、`min_engine_version:[1,21,120]` | 同左 | **一致，无冲突** |
| header/module UUID | `fb70dfb0…` / `4e00baed…` | `f7b82527…` / `d329a995…` | **交集为空**，不是 UUID 重复 |

| **PNG 签名** | 187 个 `.png`，**58 个不是 PNG** | 1108 个 `.png`，**0 个非法** | ⚠️ **重大差异** |

## 三、根因（按确定性排序）

### 主因 ① 58 个 macOS AppleDouble 伪 PNG — 确定

源 Java 材质包是在 **macOS 上打包的**，Finder 压缩会给每个文件附带一个 `._xxx` 的 **AppleDouble 资源叉**
（176 字节，头为 `Mac OS X`，**根本不是 PNG**），扩展名却仍是 `.png`。
旧版转换器 `scan()` 只按 `/\.png$/i` 过滤扩展名，把 `._sunflowers.png` 之类**当成合法基色贴图**，
`convert()` 又「原样复制」进输出包的 `textures/blocks/`。

这些伪 PNG 是**无任何 `texture_set.json` 引用的孤儿**，但基岩版加载资源包时会扫描 `textures/` 下的图片并尝试解析，
遇到非法 PNG 即写入 content error → 游戏界面报「有 1 个资源包加载错误」。
ENRO 是 Windows/规范流程打的包，0 个这类文件，所以能正常加载。

> 报告 `_pbr2vv_report.json` 里 `failures` 也留了痕迹：`'__MACOSX/.../._pif' → "PNG 头无效"`。

### 主因 ② 两个 `pbr/global.json` 全局单例叠加 — 确定（叠加场景特有）

`pbr/global.json` 里的 `minecraft:pbr_fallback_settings` 是**全局回退设置（全局单例）**。
两个包**都带 `capabilities:["pbr"]`、都定义了这个文件**，内容还不同（ENRO 的 `actors`/`items` 为 `10`，转换包全 `0`）。
多个 PBR 包叠加时会竞争同一套材质/全局定义，官方与社区资料明确记载会触发 errors / visual glitches。
这正是「**单独用不报、叠加才报**」这类现象最合理的机制层解释：单包时只有一份全局定义，叠加时两份冲突。

> 微软文档与 RTX/VV 排障资料：「Several PBR packs are conflicting — Multiple RTX/PBR packs can compete for the same
> textures or material definitions. The result may be missing textures, visual glitches, errors…」；
> 另有 add-on 更新日志记录过 PBR capability 与「是否为唯一 PBR 包」相关的引擎 bug。

### 次因 ③ 文件名含空格 / 重复 ZIP 条目 — 确定存在问题，是否触发报错视加载器而定

- `textures/blocks/grass_block_side_overlay_n .png`、`..._s .png`：基岩资源位置不允许空格。
- `textures/blocks/snow.png` 是**重复 ZIP 条目**（两张不同的 512×512 图撞名，2934 B 与 402218 B）。
  来源是 Java 的 `snow` 方块贴图与 `environment/painting` 的 `sun`/`snow` 等贴图被无差别归到 `blocks` 后同名。
  部分平台 ZIP 加载器遇到重复条目会直接判包损坏。

### 顺带发现（不直接致报错，但会贴错）

Java 的 `textures/painting/`（画：`sunflowers`/`bomb`/`wither`/`aztec`/`creebet`…）与
`textures/environment/`（`sun`/`moon_phases`/`rain`/`snow`…）贴图被塞进了 `textures/blocks/`。
共 16 个非方块纹理被当方框图输出，属目录归类过粗（映射表只按基名查表、不看目录上下文，见 `15_` 号遗留）。

## 四、明确排除的项（避免再次跑偏）

| 排除项 | 依据 |
|---|---|
| UUID 重复 | 两包 4 个 UUID 交集为空 |
| `manifest.json` 字段 / `min_engine_version` | 两包完全相同，ENRO 能加载 |
| JSON 语法 / TGA 头 / texture_set 悬空引用 | 转换包 61 个 JSON、115 个 TGA、58 个 texture_set 全部通过 |
| 封面 `pack_icon.png` | 两包都有、均为合法 PNG；封面缺失本身只是可选文件 |
| 同名 `texture_set` 的 `_mer` vs `_mers` 命名差异 | 同名文件按包优先级**整文件覆盖**，不是合并，不会致加载错误；只是两套命名体系 |

## 五、订正：我上一轮的错误猜测

我之前说过一句未核实完就给出的话：

> 「`pbr/global.json` 的 `format_version` 写在了外层，规范里它应该在 `minecraft:pbr_fallback_settings`
> **内部** —— 这会直接导致游戏解析资源包报错。」

**这个猜测是错的，本次实证推翻**：ENRO（用户确认能正常加载的商业包）的 `pbr/global.json`
同样是 `format_version:"1.21.40"` 写在**外层**，与转换包字节级写法一致。
既然 ENRO 能正常加载，外层写法就不是致错主因。真正的问题是 §三主因①（非法 PNG）
与 §三主因②（两个包都定义这个**全局单例文件**）——**与 `format_version` 的位置无关**。

同理，前几轮把「展示贴图 / 封面」当成加载报错的根因也是错的：封面是可选文件，缺失不会导致包加载失败。
（封面问题的正确结论见 `16_` 号「订正二」：那是游戏列表里的图标，与本次的 content error 是两回事。）

## 六、修复

### A. 立即可用：清洗用户这个包

`LabPBR2VV/verify/clean_pack.py`（可复用）：

```bash
python3.11 verify/clean_pack.py <输入.mcpack> <输出.mcpack> --stack
```

- 剔除 58 个 macOS `._` 伪 PNG + `__MACOSX/` + `.DS_Store`
- 剔除 2 个含空格文件名
- 兜底剔除任何「扩展名是 .png 但签名非法」的文件
- 合并重复 ZIP 条目（`snow.png` ×2 → ×1）
- **`--stack`（叠加模式）**：移除 `pbr/global.json` 全局单例，由下层 ENRO 提供回退
- 更新包内 `_pbr2vv_report.json`，新增 `cleanup` 字段记录剔除明细

产出：**`/workspace/A Multi domain 1024x 叠加修复版.mcpack`**（301 文件 / 142.2 MB）。
复验 10 项全过：非法 PNG 0、`._` 0、空格名 0、重复条目 0、JSON 全合法、TGA 全合法、
texture_set 悬空引用 0、ZIP CRC 全检通过、`pbr/global.json` 已移除。

> 若想**单独使用**（不叠加 ENRO），用 `--keep-global` 保留 `pbr/global.json` 再跑一遍即可。

### B. 治本：转换器引擎

`LabPBR2VV/LabPBR2VV.html` 8 处补丁：

1. `scan()` 新增 `isJunkPath()`：扫描入口拦截 `._` / `__MACOSX/` / `.DS_Store` / 含空格文件名，统计 `SCAN_JUNK`
2. `convert()` 基色复制**前校验 PNG 头 8 字节**，非法则整组跳过（第二道防线），统计 `invalidPng`
3. 输出名 `/\s/` / `._` 校验 + `emitted` Set **去重**，杜绝重复 ZIP 条目，统计 `dupSkipped`
4. 报告新增 `hygiene` 字段（`scanJunkSkipped` / `illegalNameSkipped` / `invalidPngSkipped` / `duplicateSkipped`）
5. 新增**「与现有 PBR 包叠加使用」复选框**（`#optStack`）：勾选后**不输出 `pbr/global.json`**，避免全局单例冲突；
   报告 `options.stackMode` 记录该状态

### C. 叠加使用方式

把**修复版转换包**与 **ENRO** 同时启用即可（转换包作为补充层）：
- 修复版已不含 `pbr/global.json` 与全部非法文件 → 不再产生 content error
- 全局 PBR 回退由下层 ENRO 提供
- 若用新版 `LabPBR2VV.html` 重新转换，**记得勾选「与现有 PBR 包叠加使用」**

## 八、仍未 100% 坐实的（如实列出）

- **「叠加才报错、单独不报错」的精确引擎机制**无法在沙箱里复现（没有基岩版客户端）。
  §三主因②是基于「两包都定义全局单例 + 官方/社区关于多 PBR 包冲突的记载」的高置信推断，
  不是游戏日志实测。但 §三主因①（58 个非法 PNG）是**确定会导致 content error** 的硬错误，与叠加与否无关。
- 沙箱无 Android SDK，APK 未编译、未做真机导入；`entity/` 目录、1.13 前旧包扁平化、动画 `.mcmeta` 仍未处理。
- 叠加时同名 `texture_set` 谁覆盖谁由游戏内包优先级决定，需在游戏里确认最终材质效果。
