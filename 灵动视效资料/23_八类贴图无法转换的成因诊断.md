# 23 · 八类贴图"无法转换"的成因诊断（两个真包逐像素实证）

> 整理日期：2026-11-16　|　用户提问：草方块侧面、矮草、向日葵下半部分、高蕨、铁砧、切石机、诡异木板、绯红木板——为什么无法转换？
> - Java 源包：`ENRO 0.20.2 主体 128x`（真包 `/tmp/enro/enro.zip`，38 MB）
> - 基岩参考：`ENRO 0.20 网易版2`（真包 `/tmp/uvcmp/bedrock.mcpack`，38 MB，作者手工适配基岩的同款材质）
> 说明：用户上传的 `.zip/.mcpack` 实际是 12 KB 的 HTML 快照，故结论全部基于上述两个真包取证。

## 一、结论先行

**这 8 类里没有一类是"转换器坏了"**——根因全在 **Java→基岩的命名 / 目录差异**，以及少数**基岩根本没有对应物**。逐像素比对发现：**10 组候选配对中有 9 组内容 100% 完全一致**，证明内容同源、只要改对名字就能转；"草方块侧面"❗§九 订正：并非作者重绘，而是 Java 的 `_overlay` 叠加层未合成（合成后与网易基岩手工适配图差 0.12），已修复。

一句话：**贴图内容是对的，是"文件名 / 文件夹名"对不上基岩的读取路径，所以游戏里看不到。**

## 三、逐类根因

转换器规则（`mapName()`）：**目录沿用 Java 原目录**（`block`→`blocks`），文件名查 478 条映射表；查不到就**原样输出**。基岩实际读取的是另一套名字/目录，于是踩空。

### 1. 矮草 / 向日葵下半 / 高蕨 —— 映射表缺条目（改名即可修）

| 源名 | 转换器输出 | 基岩实际读取 | 映射表状态 |
|---|---|---|---|
| `short_grass` | `blocks/short_grass.png` | `blocks/tallgrass.png` | ❌ 缺失 |
| `sunflower_bottom` | `blocks/sunflower_bottom.png` | `blocks/double_plant_sunflower_bottom.png` | ❌ 缺失 |
| `large_fern_bottom` | `blocks/double_plant_fern_bottom.png` | 同名 | ✅ 已有 |
| `large_fern_top` | `blocks/double_plant_fern_top.png` | 同名 | ✅ 已有 |

- 矮草、向日葵下半：映射表缺条目 → 输出 Java 原名 → 基岩按 `tallgrass` / `double_plant_sunflower_bottom` 找，找不到 → **不显示**。内容 100% 同源，补两条映射即可。
- 高蕨上下：**映射已存在且内容 100% 一致，本应能转**。若仍不显示，检查是否输出包里 `double_plant_fern_*_mers.tga` 缺失（该组 Java 只有 `_s`、无 `_n`，MERS 由 `_s` 生成，正常）。

### 2. 诡异木板 / 绯红木板 —— 目录层级不同（改目录即可修）

- 转换器输出 `textures/blocks/warped_planks.png`、`crimson_planks.png`
- 基岩实际在 `textures/blocks/huge_fungus/warped_planks.png`、`crimson_planks.png`
- 内容 100% 同源，只是少了一层 `huge_fungus/` 目录 → 基岩读不到。
- **注意**：这是"目录"差异，不是文件名差异；当前 `mapName()` 只会改文件名、不改目录，所以映射表加条目也解决不了，需要支持"目标目录重定向"。

### 3. 切石机 —— 部分同名能转，部分基岩无对应

| 源名 | 基岩情况 | 结论 |
|---|---|---|
| `stonecutter_bottom` / `saw` / `top` | 基岩有精确同名，内容 100% 一致 | ✅ 应能直接转换 |
| `stonecutter_side` | 基岩**没有** `stonecutter_side`，用 `top` 兼作侧面 | ⚠️ 无对应物，输出也不会被读取 |

- 另注意 Java 侧 `stonecutter_side_S.png` 用**大写 `S`** 作后戳，虽然扫描正则 `/(_s|_n)?\.png$/i` 忽略大小写、能正确归组，但属于源包的不规范命名。
- 若 `stonecutter_bottom` 等"同名能转"的也不显示，多半是**同包的 PBR 叠加冲突**（见 17 号文档）或 MERS 通道名不匹配，而非贴图本身。

### 4. 铁砧 —— 命名差异（❗本段已被 §八订正）

> **订正（2026-11-17）**：本段"基岩无铁砧贴图"是**只搜了网易参考包**导致的误判。查 Mojang 官方 `bedrock-samples v1.26.70` 实物，铁砧 VV 贴图 **4 张齐全**（`anvil_base` + `anvil_top_damaged_0/1/2`，各带 `_mers.tga` 与 `.texture_set.json`，16² 占位图）——基岩侧**有目标可覆盖**。真正原因是 L1 命名差异，已修复，详见 §八。以下保留原始推理过程。

- Java 有 `anvil.png` / `anvil_top.png` 等；
- 网易参考包搜 `anvil` = **0 个文件**（该网易包作者未给铁砧做 VV 材质，沿用原版默认外观）。
- 映射表自然也没有 → 转换器原样输出 `blocks/anvil.png`，但基岩 VV 不会去读它。
- **（原）结论**：不是转换失败，是**基岩侧没有可覆盖的目标**。→ 此结论仅对"网易包"成立，对官方 VV 机制不成立。

### 5. 草方块侧面 —— ❗§九 已订正并修复（原误判为"唯一内容不同"）

> **订正（2026-11-17）**：本节两处疏漏——① 只搜 `.png` 漏看官方 `grass_side.tga`（目标其实存在）；② 拿 Java 纯基色去比**覆雪变体** `grass_side_snowed`（差 23.78），既选错目标又没合成 overlay。真实机制与修复见 §九。以下保留原始推理。

- Java `grass_block_side.png` 有独立的 `_overlay.png` 叠加层（草的边沿溢出色，alpha 占 17.6%）；
- 基岩没有 `_overlay` 概念，作者把草边**烘焙**进 `grass_side` / `grass_side_snowed`；
- （原）两者平均差 23.78 → 判为"作者重绘"；实际是**纯基色 vs 覆雪变体**的错位对比；
- （原）声称基岩"没有 grass_side" → 实际官方有 `grass_side.tga`（只搜 .png 漏看）；
- **（原）结论**：改名也不等价 → 此结论错误。❗§九 证实：合成 overlay 后与网易基岩图差 0.12，已修复。

## 七、基于最新产物的深层复查（2026-11-17，用户再问 7 类）

用户再次列出 7 类（矮草、草方块侧面、高蕨、铁砧、切石机、诡异木板、绯红木板）问"为何无法转换"。此时 §六 的映射/目录修复**已落地**（矮草→tallgrass、木板→huge_fungus 均已生效）。本次用三个真包（Java `enro.zip`、Mojang 官方 `official.zip`、网易基岩 `bedrock.mcpack`）+ 最新产物逐层复查，结论比 §一~§六 深刻得多：

> **"转换成功" ≠ "游戏里生效"。产出的文件几乎全对（基色逐像素 100% 一致），看不到是四层机制叠加的结果。**

### 四层根因模型（关键）

1. **L1 命名/目录层**：Java 名 ≠ 基岩名 → 已由 §六 修复（矮草、向日葵底、木板目录）。
2. **L2 基色格式优先级层**：官方某些目标基色是 `.tga`；基岩按 **`.tga > .png > .jpg > .jpeg`** 取图（05 号文档 §170）。若产物写成 `.png` 而官方自带同名 `.tga`，**官方 tga 占位符压制产物 png**。
3. **L3 texture_set 叠加层**：同一纹理集**不合并**，高优先级包整份覆盖；且引用**只能指向本包内**贴图，高优先级包的同名图不顶替（10 号 §186 / 13 号 §109）。
4. **L4 基岩侧无目标层**：基岩根本没有该贴图的 VV 定义，产出无处覆盖。~~（原把铁砧归此层，❗§八 订正：铁砧其实有目标，属 L1）~~ 本批 7 类经复查后**无一属真正的 L4**。

### 逐类判定（最新产物）

| 类别 | 转换后目标 | 基色像素 | 格式 | 真正能否显示 | 根因层 |
|---|---|---|---|---|---|
| 矮草 `short_grass` | `tallgrass` | 100% 一致 | **产物 png / 官方有 tga(16²占位)** | ⚠️ 很可能被官方 tga 压制 | L2（**白名单 `TGA_BASE` 漏了 `tallgrass`**）|
| 草方块侧面 `grass_block_side` | `grass_side` | 纯基色100%（缺overlay） | tga ✓ | ⚠️ overlay 未合成（❗§九已修）| L5 叠加层合成（新层）|
| 高蕨 `large_fern_*` | `double_plant_fern_*` | 100% 一致 | tga ✓（在白名单）| ✅ 应能显示 | 无（若失败查 L3 叠加）|
| 铁砧 `anvil` | ~~`anvil`~~ → `anvil_base` 等4名 | 100% 一致 | png | ✅ 官方有 4 张 VV 贴图可覆盖（❗§八订正）| **L1 命名差异**（已修）|
| 切石机 `stonecutter_*` | 同名 | 100% 一致 | png ✓ | ✅ 应能显示（`side` 基岩无对应）| 无 / L4(side) |
| 诡异/绯红木板 | `huge_fungus/*` | 100% 一致 | png ✓ | ✅ 应能显示（§六目录已修）| 无（已修）|

### 决定性发现：`_mer` vs `_mers` 不是 bug

网易参考包 MERS 用 `_mer`（349 个），曾疑为产物 `_mers.tga` 不匹配。**Mojang 官方包 3175 个全用 `_mers`、0 个 `_mer`** —— 产物 `_mers.tga` 才是正解，网易包 `_mer` 是旧教程格式（11 号文档已证）。此项排除。

### 唯一确凿待修项：矮草 tallgrass

- 官方包 `tallgrass` **同时有 16×16 的 `.png` 和 `.tga` 占位图**；
- 转换产物 `tallgrass` 是 **128×128 真实贴图、格式 png**；
- 白名单 `TGA_BASE` 含 `tallgrass_carried` 却**漏了 `tallgrass`** → 产物写成 png；
- 按 `.tga > .png` 优先级，叠加时官方 16×16 tga 占位符可能压制我们的 128×128 png → 表现为"矮草没生效"。
- **修法**：把 `tallgrass` 加入 `TGA_BASE` 白名单，产物改写 `tallgrass.tga`（128×128），与官方同格式同扩展名，靠包优先级覆盖。

### 结论

§六 修的是 L1（命名/目录），本次定位到 L2（格式优先级）还有一个遗漏点（tallgrass）。其余类别要么本来正常（高蕨/切石机/木板）、要么内容重绘非格式问题（草侧面）。~~本轮为分析，未改代码；tallgrass 白名单补录待用户确认后执行。~~ **tallgrass 已于 2026-11-17 修复（见修复落地小节）；铁砧原判 L4 无解亦于同日订正为 L1 并修复（见 §八）。**

## 八、基岩铁砧如何上材质 + 铁砧映射修复（2026-11-17）

用户追问"铁砧的基岩版是如何上材质的"，据此复查官方包并**推翻 §四/§七 的"L4 无解"误判**。

### 8.1 基岩铁砧的上材质机制（官方 bedrock-samples v1.26.70 实物）

铁砧是**体素模型 + 4 张命名贴图 + 方块状态选面**三段式：

1. **模型**：`behavior_pack/shapes/anvil.json` 用 7 个 box（voxel_shape）拼出底座/腰身/砧面；UV 由客户端内置材质槽分配，不在形状文件里。
2. **贴图**：`resource_pack/textures/blocks/` 下 4 张，各配 `_mers.tga` + `.texture_set.json`（16² 占位图）：
   - `anvil_base.png` —— 底座/侧面，4 种损伤状态通用；
   - `anvil_top_damaged_0/1/2.png` —— 砧面顶面，对应完好/微损/重损。
3. **选面**：方块状态 `damage`（0/1/2）决定用哪张顶面；底座图不变。这就是"完好/微损/重损铁砧"外观差异来源。

### 8.2 误判根源

§四 当初判定"基岩无 anvil 贴图、无解"，是**只搜了网易参考包**（该包作者未给铁砧做 VV，搜 anvil=0）。官方 VV 机制里铁砧**有完整 4 张目标**，属 **L1 命名差异**（与矮草同类），可修。

### 8.3 修复落地

Java 4 名 → 基岩 4 名，映射表补 4 条（480 → **484**）：

| Java 源名 | 基岩目标名 | 部位/状态 |
|---|---|---|
| `anvil` | `anvil_base` | 底座/侧面 |
| `anvil_top` | `anvil_top_damaged_0` | 顶面·完好 |
| `chipped_anvil_top` | `anvil_top_damaged_1` | 顶面·微损 |
| `damaged_anvil_top` | `anvil_top_damaged_2` | 顶面·重损 |

- `mapping/build_map.py` MANUAL 补录 4 条，逐条经官方实物存在性断言（4 张 texture_set 齐全）。
- `name_map.json` 重生成 484 条；HTML 内嵌 `BUILTIN_MAP` 同步 484，`BUILTIN_MAP_SIZE=484`（脚本重写，与 JSON 完全一致）。

## 九、草侧面的名字核实 + overlay 合成修复（2026-11-17）

用户追问"搜一下草侧面的名字"→"修复了吗"。据此复查并**发现真 bug、已修复**。这是 8 类里最后一处实质问题。

### 9.1 草侧面的名字（官方 bedrock-samples v1.26.70 实物）

搜 `textures/blocks/*grass*`，草方块侧面相关 4 个：

| 基岩名 | 含义 | 格式 | 有 VV |
|---|---|---|---|
| **`grass_side`** | 普通草侧面 | **16² tga 占位** | ✅ |
| `grass_side_snowed` | 覆雪草侧面 | png + tga | ✅ |
| `grass_side_carried` | 手持形态侧面 | png | ✅ |
| `grass_top` / `grass_block_snow` | 顶面 / 覆雪顶 | png | ✅ |

- **核心答案：基岩草侧面就叫 `grass_side`**（对应顶面 `grass_top`）。§四"没有 grass_side、只有 _normal/_snowed"是**只搜 .png 漏看 `grass_side.tga`** 的疏漏。
- Java 侧 `grass_block_side` 有两张：`grass_block_side.png`（基色）+ `grass_block_side_overlay.png`（叠加层，alpha 占 17.6%）。**基岩无 overlay 概念**，作者把草边烘焙进基色。

### 9.2 真 bug：overlay 未合成

之前转换器把 `grass_block_side.png` **纯基色**直接写成 `grass_side.tga`，丢掉 overlay 草边。决定性证据（网易手工适配基岩包 `grass_side.tga` 为基准）：

| 对比 | RGB 平均差 |
|---|---|
| 旧产物（纯基色）vs 网易基岩图 | **13.20** |
| 基色+overlay 合成 vs 网易基岩图 | **0.12**（同源，量化误差）|

即之前差 13.20 不是"作者重绘"，而是**缺了 overlay 那一层**——§四/§七 的 23.78 还叠加了"错比覆雪变体"的二次错误。

### 9.3 修复落地

`LabPBR2VV.html`：

| 改动 | 内容 |
|---|---|
| 新增 `OVERLAY_SRC` | `{ grass_side: 'grass_block_side_overlay' }`——目标基岩名 → Java overlay 源基名 |
| 新增 `OVERLAY_ONLY` | `Set(['grass_block_side_overlay'])`——纯叠加层组跳过 |
| 基色段合成 | 转换 base 时解码 overlay，按 `out.rgb = ov.rgb*a + base.rgb*(1-a)`、`out.alpha = base.alpha` alpha 合成，再按目标格式编码 |
| 跳过 overlay 组 | `grass_block_side_overlay` 不再单独输出（基岩无此文件）|
| 报告新增计数 | `overlayComposited` / `overlaySkipped` |

### 9.4 验证结果（真包端到端）

| 检查项 | 结果 |
|---|---|
| 报告计数 | `overlayComposited:1`、`overlaySkipped:1`；converted 451→450，文件 1399→1396 |
| 产物 grass 条目 | 仅 `grass_side.tga` + `_mers` + `.texture_set.json`；3 个 `grass_block_side_overlay.*` 冗余文件消失 |
| 新产物 vs 理论合成图 | **RGB 差 0.00、100% 一致**（合成算法精确）|
| 新产物 vs 网易基岩图 | 差 0.12（同源）|
| 新产物 vs Java 纯基色 | 差 13.08（证明 overlay 已烘焙）|
| 静态检查 / CRC | 46/46 / 全包 CRC 通过 |

- 新产物：`ENRO 0.20.2 主体 128x 转换版.mcpack`；修复前备份 `ENRO_0.20.2_preGrassOverlayFix.mcpack`。
- **至此 8 类全部结案**：无一属真正的 L4；L1（命名/目录）、L2（格式）、L5（overlay 合成）全部修复；L3 属多包规则。

> 新增根因层 **L5 叠加层合成层**：Java 部分贴图靠独立 `_overlay.png` 表达叠加效果，基岩要求烘焙进基色，转换器须主动 alpha 合成——这是四层模型之外的新发现。
