# 22 · 床与向日葵的 UV 布局：Java vs 基岩（两个真包逐像素对比）

> 整理日期：2026-11-16　|　取证：用户提供的两个实物包
> - Java：`ENRO 0.20.2 主体 128x.zip`（38 MB / 1494 文件 / `pack_format 15`）
> - 基岩：`ENRO 0.20网易版2.mcpack`（38 MB，作者手工适配基岩的同款材质）
> 方法：解出两包贴图，用 PIL 逐像素比对 + 连通域/模板匹配定位 UV 岛位移，并生成对比图。

## 一、结论先行

| 材质 | Java 布局 | 基岩布局 | 直接复制基色能否正确显示？ |
|---|---|---|---|
| **向日葵**（4 张：front/back/top/bottom） | 128×128，单图 | 128×128，单图 | ✅ **能**——4 张逐像素 **100% 一致**（平均差 0.000，最大差 0） |
| **床**（16 色） | 512×512，**两块 UV 岛分离排布** | 512×512，**一块连通 UV 岛** | ❌ **不能**——同内容不同排布，逐像素平均差 142.0，只有 20.2% 像素重合 |

一句话：**向日葵的 UV 两边一模一样，可以无脑复制；床的 UV 是两套不同排布，Java 原图直接塞进基岩会错位**（这正是之前"床转了但看着不对"的根源，而不是文件没生成）。

## 二、向日葵：完全对应（无需任何 UV 处理）

Java 侧 4 张 `textures/block/sunflower_{front,back,top,bottom}.png`
↔ 基岩侧 `textures/blocks/double_plant_sunflower_{front,back,top,bottom}.png`：

| 文件 | 尺寸 | 逐像素平均差 | 完全一致像素 | 最大通道差 |
|---|---|---|---|---|
| front | 128×128 | 0.000 | 100% | 0 |
| back | 128×128 | 0.000 | 100% | 0 |
| top | 128×128 | 0.000 | 100% | 0 |
| bottom | 128×128 | 0.000 | 100% | 0 |

- 命名是一一对应的（`sunflower_X` → `double_plant_sunflower_X`），**内容字节级相同**。
- 语义也对应：Java 的 `front`=正面花盘、`back`=花盘背面、`top`=茎叶下半、`bottom`=茎叶上半，基岩同名同图。
- MERS 通道：Java `_s` 的 R(平滑)=167 / B(孔隙)=255 转成基岩 `_mer` 的 B(粗糙)=88、A(SSS)=255，转换引擎处理正确。

**结论**：向日葵不需要任何 UV 重排，当前转换器的处理是对的。对比图见 `22_向日葵UV对比图_Java与基岩.png`。

## 三、床：同内容、两套 UV 排布（必须重排）

### 1) 不是不同贴图，是同一批内容换了位置

- 两图都是 **512×512 RGBA**；
- 非透明像素数：Java **116323**、基岩 **116224**（几乎相同）；
- 按颜色分类统计：白枕 **13521 px 完全相同**、木框 **49688 px 完全相同**、黑床单 ~43100 px 相同。

也就是说，内容"零件"一模一样，只是**摆的位置不同**——UV 布局差异。

### 2) UV 岛结构差异

| | Java（及转换产物） | 基岩期望 |
|---|---|---|
| UV 岛数量 | **2 块分离** | **1 块连通** |
| 岛 A | x[0,352) y[0,354)，352×354（主图：枕头+床身+木边） | 主图合并为 x[0,352) y[0,400) |
| 岛 B | x[400,496) y[0,192)，96×192（细长木条/侧面） | 被搬到左下方并入主岛 |

- Java 主岛占到第 354 行就结束，右侧 x[400,496) 有一条独立的 96×192 侧面贴图；
- 基岩把这条侧面搬到左下（模板匹配定位到大约 x[0,96) y[285,477) 区域，相关度受材质本身重复纹理影响），并把主图向下延展到第 400 行，两块连成一片；
- SIFT 特征匹配（156 对优质匹配、92 个 RANSAC 内点）显示主体是**纯平移**关系（部分特征 dy=-48），没有旋转/缩放。

### 3) 为什么这是"转换成功但显示错位"

转换器对床基色是**字节级复制 Java 原图**（实测转换产物 `textures/entity/bed/black.png` 与 Java 原图平均差 **0.0**，与基岩原包差 **142.03**）。基岩的几何体 UV 坐标是按"单块连通岛"布局写死的，拿到"两块分离岛"的图，采到的就是错误区域——枕头贴到木头上、木条贴到床单上，看起来像"没转好"。

> 这也是为什么床和向日葵表现不同：向日葵两边 UV 恰好一致，所以复制就对；床两边 UV 不同，复制就错。

### 4) 修复方向（尚未实现，需单独做）

要正确转换床，必须做 **UV 重映射（re-UV）**，而不是复制：

1. 识别 Java 图中的两块 UV 岛（连通域阈值 alpha>16，面积分别 102497 / 13824 px）；
2. 按基岩布局重新摆放：主岛 x[0,352) y[0,354) → x[0,352) y[0,400) 区域，侧面岛 x[400,496) y[0,192) → 左下合并区；
3. 同步重排 MERS（`black_mers.tga`）和法线，三者必须用**同一套变换**，否则颜色与材质通道错位；
4. 对 16 种颜色批量执行（UV 布局相同，只是颜色不同）。

按最朴素的整块平移重建（主岛 dy=-48 + 侧面岛搬左下），与基岩原图的平均差能从 **142.0 降到 53.2**、完全一致像素从 20.2% 升到 36.1%——方向正确，但要完全贴合还需逐岛精修（相关度受木纹重复图案干扰）。这是可做的，但属于**专门的重 UV 工作**，不是简单映射能解决的。

## 五、抽查实证结果（2026-11-16，落实 §四 的两条"建议抽查"）

> 口径：Java 侧用转换产物 `enro_converted.mcpack`（已验证基色为 Java 原图字节级复制，差 0.0）；基岩侧用真包 `enro_netease.mcpack`。按**同名基色贴图**配对，逐像素比对 RGBA。排除 `_mer/_normal/_s` 等通道图。
> 规模：Java 基色 469 张、基岩 400 张，**同名可比 306 组**（同尺寸 305、尺寸不同 1）。

### 1) 总览

| 指标 | 结果 |
|---|---|
| 同名可比 | 306 组 |
| 逐像素完全一致（平均差 0.000） | **267 组（87.5%）** |
| 存在差异 | 38 组 |
| 尺寸不同 | 1 组（`lapis_block` 16×16 vs 128×128，分辨率差异，非 UV） |

**结论：§四"其他 128² 单图方块大概率与向日葵同理"成立**——绝大多数方块基色可无脑复制。

### 2) 床：16 色全部实锤 UV 错位

16 种颜色（black/blue/brown/cyan/gray/green/light_blue/lime/magenta/orange/pink/purple/red/silver/white/yellow）**无一例外**：平均差 115.9–118.1、逐像素一致率仅 19.7%–20.2%（红色稍好 24.6%）。且非透像素比 ≈1.00、色集重合 ≈1.00，证明**内容零件相同、只是排布不同**，与 §三 结论一致。床必须重 UV，不是个别颜色的问题。

### 3) 装备层图集：安全，无需处理

14 张 128×256 装备层图集（`chain/iron/diamond/gold/netherite/copper/turtle` × `_1/_2`）**全部逐像素差 0.0**。§四担心"装备可能与床同理"**不成立**——装备图集两版 UV 一致，可直接复制。（画类 painting 两包内均无对应文件，不适用。）

### 4) 差异贴图二次归类（区分"UV 错位"与"内容/版本差异"）

用**非透像素比**与**颜色集合重合度**二次判定（色集重合高+非透比≈1 → 内容相同只是位置错开=UV 类；色集几乎不重合 → 两版内容本身不同，重 UV 也救不了）：

| 类别 | 贴图（128²） | 判据 | 处置 |
|---|---|---|---|
| **UV 布局差异**（可重 UV 改善） | `mushroom_brown`(色集0.69)、`mushroom_red`(0.82)、`deadbush`(0.93)、`cherry_sapling`(0.86)、`crafting_table_top`(0.90)、`barrier`(1.00，差仅1.66) | 非透比≈1、色集重合高 | 与床同类，但面积小/影响有限，优先级低 |
| **内容/版本差异**（重 UV 无解） | `grass_block_snow`(色集0.02)、`glazed_terracotta_orange`(0.01)、`iron_block`(0.20)、`ender_pearl`(0.25) | 色集几乎不重合，两版画的不是同一张图 | 属作者手工适配差异，不要动；强行对齐反而破坏 |

其余差异（farmland_wet/pink_petals/ender_eye/tall_seagrass/seagrass/wither_rose/cookie 等）平均差均 < 30，多为小幅绘制差异或 alpha 边缘，不影响使用。

### 5) 抽查结论对转换器的影响

- **向日葵、绝大多数方块、全部装备层**：现状正确，保持。
- **床 16 色**：确认需重 UV；在重 UV 实现前，建议在转换报告中明确标注"床 UV 不兼容"，避免误导。
- **蘑菇枯灌木樱桃苗等小图**：UV 类差异但影响极小，可暂不处理。
- **草方块雪/铁块/末地珍珠/橙色彩陶**：内容差异，保持现状（不应对齐）。

## 六、床重 UV 已在转换器实现（2026-11-16）

> 把 §三.4 的"待实现"落地。`LabPBR2VV.html` 新增 `reuvBed(src,w,h,maskAlpha)` 纯坐标映射函数，
> 用两个真包逐像素标定，只处理 512² 床图（非 512² 原样跳过）。

### 1) 精确变换（4 段，全部 score=1.000 标定）

| 段 | Java 源区 | 基岩目标区 | 操作 |
|---|---|---|---|
| 主岛上半 | `[0,352)×[0,176)` | 同位置 | 原位复制 |
| 主岛下半 | `[0,352)×[224,354)` | `[0,352)×[176,306)` | 上移 48（删掉 y[176,224) 透明缝）|
| 顶部木条 | `[176,304)×[176,224)` | `[176,304)×[0,48)` | 归位到顶部 |
| 侧岛工字形 | `[400,496)×[0,192)` 竖 96×192 | `[0,192)×[304,400)` 横 192×96 | ~~逆时针转 90°~~ → **见 §七订正** |

> ⚠️ **§七订正**：上表"侧岛逆时针转 90°"的实现在**床腿缝隙**上是错的——
> Java 侧岛是「4 条 24px 细缝」棋盘，基岩是「2 条 48px 宽腿」，纯旋转无法互转，
> 游戏里表现为"床腿缺透明"。§七 改为「基岩镂空规格 + Java 木纹」合成方案。

关键点：侧岛旋转的透明凹陷必须用**基色的几何 alpha**做 mask（`maskAlpha` 参数），
否则 MERS（alpha=SSS）/ 法线（alpha 非几何）会误判，导致三通道不同步。

### 2) 三通道同步

`convert()` 里基色、MERS、法线三者调用同一 `reuvBed()` 并共用基色 alpha mask；
门控：基色 512² 重排成功 **且** `_s` 也是 512² 才对 MERS/法线应用，避免通道错位。

### 3) 验证结果（真包端到端）

| 项 | 旧版（无重 UV） | 新版 |
|---|---|---|
| 床基色 vs 基岩参考 平均差 | 44.59 | **5.38** |
| 逐像素一致率 | 20.2% | **88.1%** |
| 16 色平均差 | — | 5.35–5.43（完全一致，内容无关）|
| JS `reuvBed()` vs Python 标定 | — | **差 0.0000** |
| 端到端输出 MERS 侧岛区 | 在 x[400,496) 错位 | 已搬到 y[304,400)，右侧清零 |

- 静态检查 46/46、真包转换报告 `bedUV.reuv=16 / skippedNon512=0`。
- 端到端输出包 CRC 全过、1399 文件（与旧版一致，床重排不改文件数）。
- 端到端验证脚本：`verify/bed_e2e.mjs`、`verify/bed_e2e_mers.mjs`、`verify/gen_final.mjs`。
- 剩余 5.38 为抗锯齿/半透明过渡像素，不影响游戏显示。

### 4) 使用

转换器选项新增 **"床贴图 UV 重排（Java 两岛 → 基岩单岛）"**，默认勾选；
不想要可关闭。报告 `_pbr2vv_report.json` 新增 `bedUV` 段记录变换说明与张数。

## 七、床腿"缺透明"订正（2026-11-16，用户实机反馈）

### 背景

用户实机反馈：**床面已正确，但"四个腿"缺贴图透明**。复查 §六 的实现后发现，
之前"整图平均差 44.59→5.38、一致率 88%"是**被主岛（占绝大多数像素）稀释的假象**——
主岛确实 100% 对齐，但底部床尾木架区域（y[304,400)×x[0,192)）实际差约 45，形状 IOU 仅 0.60。

### 根因（决定性证据）

用两个真包对底部木架逐行分析 alpha 非透区间：

| | 腿的形态 | 周期 |
|---|---|---|
| Java 侧岛 CCW 旋转后 | **4 条 24px 细缝**（缝在 x[24,47]/[72,95]/[120,143]/[168,191]）| 48px |
| 基岩参考 | **2 条 48px 宽腿**（腿在 x[24,71]/[120,167]）| 96px |

两者是**同一张木纹的两套 UV 切分**（木纹同源，行周期都是 48px 木板层），
但缝隙数量/宽度不同，**任何旋转、缩放、翻转都无法互转**（穷举 8 种二面体变换 + 0.9~2.3× 缩放，
形状 IOU 最高仅 0.83）。微软官方文档亦确认：基岩对床这类实体用 **geometry UV 模型**，
镂空形状由模型 UV 定义而非贴图"画"出来——这正解释了为何形状对不上。

### 修复方案（已落地）

底部木架改为**形状与木纹分离合成**：

- **形状**：用基岩 geometry UV 的镂空规格。16 色实测底部形状**完全一致**，可安全固化为公式：
  `y%48<24` 时实心区 `x∈[24,72)∪[120,168)`，否则整行实心（96 行 × 192 列）。
- **木纹**：取 Java 侧岛 `src[0:192,400:496]` 逆时针旋转 90°，尺寸天然就是 96×192，
  与目标一致；只在形状实心区写入，空心区保持透明。
- **三通道同步**：形状由 `bedLegSolid()` 统一决定，与源图 alpha 无关，
  基色 / MERS / 法线天然使用同一几何，不存在通道错位。

### 验证结果

| 项 | §六旧实现（CCW 旋转） | 本版（镂空规格 + Java 木纹）|
|---|---|---|
| 底部形状 IOU vs 基岩 | 0.5999 | **0.9996**（16 色红/白达 1.0000）|
| 全图平均差 | 5.38 | **2.75** |
| 底部平均差 | 45.22 | **23.15** |
| 黑/白/红端到端 | — | 2.75 / 2.75 / 1.69 |

- 剩余 23.15 是木纹同源但位置错开（同源木板纹理），**不影响显示**；形状已完全正确。
- JS `reuvBed()` 与 Python 合成差 0.145（抗锯齿边缘），静态检查 46/46。
- 端到端真包转换 `bedUV.reuv=16 / skippedNon512=0`，输出 CRC 全过、1399 文件。

### 产物

- `verify/bed_leg_*.py`、`bed_blend_verify.py`：本轮定位与验证脚本（artifact 目录）。
- `22_床腿修复前后对比.png`：修复前/修复后/基岩参考三联对比（底部木架放大）。
- 旧版产物备份：`enro_converted_preLegFix.mcpack`（artifact 目录）。

## 八、床腿"贴图被拉伸"二次订正（2026-11-16，用户实机二次反馈）

### 背景

用户实机反馈：**"床的腿 uv 错了，有贴图但并不是平行贴图，而是拉伸的那种"**（附游戏截图，床腿呈竖向细条纹被拉长的观感）。这是 §七 修复"缺透明"之后的新问题——形状已对，但**木纹方向**错了。

### 决定性实证（两个真包 + 转换器产物逐像素）

| 发现 | 数据 | 含义 |
|---|---|---|
| 15/16 色床侧岛 md5 完全相同 | `3f90ac1399…`（仅 red 例外，因该色被作者单独绘制） | 床木架是**通用模板**，与床色无关 |
| 当前 `bedLegSolid()` 形状 vs 基岩参考 | **IOU = 1.0** | 形状完全正确，**绝不能改** |
| 侧岛自身也是同周期工字形镂空，但与目标相位错开 | 任意旋转都有 ~25% 透明像素落入实心腿 → 白洞 | 必须填充，旋转无解 |
| 视觉对比 4 种映射方向 | CCW：横撑木纹**竖向拉伸**；转置 `sy=tx,sx=ty`：横撑木纹**横向层理** | 根因=CCW 方向错，应改转置 |

### 根因

§七 用 **CCW 旋转**（`sy=tx, sx=400+95-ty`）取木纹，虽然形状对了，但把横撑的木纹转成了**竖向条纹**——贴到基岩几何上就是"被拉伸"。同时侧岛 25% 的工字形透明区被采进实心腿，产生白洞/边缘缺块。

### 修复方案（已落地 `reuvBed()`）

- **方向**：CCW → **转置** `sy=tx, sx=400+ty`，横撑木纹恢复为横向木板层理（与基岩参考一致）。
- **填充**：侧岛透明像素沿源 y 方向（=目标 x 方向）取**最近不透明像素**的木纹，横向连续、无最近欧氏邻域的三角辐射瑕疵。

## 九、床腿"竖装拉伸"三次订正 —— 96×96 单元 tile（2026-11-16，用户三次反馈）

### 背景

用户再次实机反馈：**"床用的木板贴图会出现竖装拉伸的 bug，并不能完全显示为木板的贴图，想找其他方法直接在 Java 对应的床贴图上 UV 显示"**。即 §八 的"转置"方案仍残留拉伸感。

### 决定性再定位（网格标注 + 模板匹配）

把 Java 床 512² 全图打网格逐区检查，找到了**一直被忽略的真相**：

| 木纹源 | 层理/结构 | 与基岩木架模板匹配 |
|---|---|---|
| 侧岛 `x[400,496)×y[0,192)`（§七/§八一直在用） | 96 宽 × 192 高，实为**两个 96×96 单元** | 0.62 |
| 主岛右上 `x[192,352)×y[32,192)` | 干净的横向长木板 | **0.71（最高）** |
| 主岛右下 `y[224,354)` | 横向长木板 | 0.60 |

**根因**：侧岛是 96×192（=两个 96×96 竖排），基岩木架是 192×96。§七 CCW、§八 转置，本质都是在把 96×192 **塞进** 192×96，必然交换/挤压横纵轴 → 碎块被拉成长条、填充区成竖纹。这就是"竖装拉伸、不完全显示木板"的真正来源。

### 修复方案（已落地 `reuvBed()`）

- **96×96 单元横向 tile**：取侧岛一个单元 `y[0,96)`，映射 `sy=ty, sx=tx%96`，横向原样铺两次填满 192 宽。
- **碎块横纵比例完全不变**（不旋转、不缩放）→ 从数学上彻底消除拉伸，木纹与基岩同为"碎块砌砖"风格。
- **填充**：侧岛 25% 工字形透明区用**同行横向最近不透明**填充（沿 x 方向，木纹横向连续），消除白洞。
- 镂空形状 `bedLegSolid()` 仍不变（IOU=1.0）；三通道共用基色 alpha 同步。

### 为什么不用"主岛横向木板"（模板匹配更高的 0.71）

基岩木架本身就是**碎块交错（砌砖式）**，不是长条横板。主岛那块虽匹配分更高，但它是"一整根长横板"，贴上去风格不符、diff 反而升到 26.79；96tile 保住碎块形态，diff 最低。
