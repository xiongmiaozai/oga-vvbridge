## 一、这一轮做了什么

前几轮已经把「资料 → 结构分析 → 官方包校验 → 通道/格式 → App 设计 → 网页原型 → Android 骨架 → 名称映射表」全部铺完，但都停留在**静态产物**：JS 只做过语法检查，转换算法只做过纯函数断言，从没有在真实浏览器里把「上传 zip → 转换 → 导出 .mcpack」完整跑一遍，也没有拿官方 3,171 组 MERS 做回归。

本轮补上设计文档（`14_` 号）§8 测试策略里明确列为待办的**集成测试**与**端到端产物校验**，并把验证脚本固化成可复跑的工程资产。结果是：跑通了，也**抓出并修掉两个真 bug**。

| 层 | 手段 | 结果 |
|---|---|---|
| L1 静态一致性 | 双端引擎比对、JS 语法、映射表、Manifest 零权限 | **24/24** |

**复核既有结论，全部通过**：

| `12_`/`13_` 号结论 | 实测 |
|---|---|
| 3,171 个 `_mers.tga` / 3,171 个 `.texture_set.json` | ✓ 严格 1:1 |
| 32-bit 2,885 个 / 24-bit 286 个 | ✓ 完全一致 |
| 全部 `format_version:"1.21.30"` | ✓ 3,171/3,171 |
| 全部用 `metalness_emissive_roughness_subsurface`，无 MER | ✓ `_mer.png` = 0 |
| `manifest.json` 为 `[1,26,70]` 且**无** `capabilities` | ✓ |
| JSON 里的引用值不带扩展名 | ✓ 0 例 |
| `iron_block_mers.tga` 首像素 `(191,0,176,0)`、均值 `R=191.0 / G=0 / B=136.7 / A=0` | ✓ 实测 136.742 |

**三处新发现**（`13_` 号已补记）：

1. **23 个 TGA 是上左原点**：`descriptor=40`（0x28 = `y_top=1` + 8 alpha bits），而其余 3,148 个是 `descriptor=8`/`0`（左下原点）。分布：blocks 17、items 5、particle 1，集中在 `icicle_*`、`jukebox_*`、`polished_calcite_*`、`calcite_pillar_*` 等新方块。**影响**：本转换器自己按左下原点写出，不受影响；但任何把官方 TGA 当输入解析的工具必须读 descriptor 判断行序，不能写死。
2. **常量数组引用**：`resource_pack/textures/flame_atlas.texture_set.json` 的 MERS 字段不是贴图名，而是常量数组 `[0, 255, 255, 0]`。规范允许用常量代替贴图，这是官方包里唯一一例。转换器目前只输出贴图引用，可考虑作为「无 `_s` 时的轻量回退」备选（比 `pbr/global.json` 更精确）。
3. **跨目录冗余**：`textures/blocks/straw_bed_particle_mers.tga` 没有同目录 texture_set，其对应的 `textures/particle/straw_bed_particle.texture_set.json` 在 particle 目录。属于官方包自身的散落文件，不是配对错误。

**round-trip 误差**（反解官方 MERS → 逆推 LabPBR `_s` → 再用 `labpbrToMers` 转回，共 **5,687,059** 个 32-bit 像素）：

| 通道 | 浮点逆推 平均/最大误差 | ≤1 占比 | 8-bit 量化逆推 平均/最大 | ≤1 占比 |
|---|---|---|---|---|
| R 金属度 | 4.179 / 191 | **93.34%** | 4.179 / 191 | 93.34% |
| G 自发光 | 0 / 0 | **100%** | 0.0001 / 1 | 100% |
| B 粗糙度 | 0 / 0 | **100%** | 0.2542 / 1 | 100% |
| A 次表面 | 0.1354 / 255 | **99.94%** | 0.15 / 255 | 99.94% |

结论：

- **平方项公式与自发光换算完全自洽**：粗糙度、自发光在浮点逆推下误差为 0；即使把 `_s` 量化回 8-bit，误差也 ≤1（这正是真实贴图的存储精度）。`14_` 号 §8 要求的「误差 ≤1」在这两个通道上达标。
- **金属度是主要损失源**：官方 MERS 有 **389,191 个像素（6.84%）使用 0/255 之外的连续金属度**（铁块均值 191）。而 LabPBR 的 `_s` G 通道只区分「介电质 F0(0–229)」与「硬编码金属(230–255)」，转换只能二值化为 0 或 255 —— 与 6.66% 像素未达 ≤1 高度吻合。这是**规范层面的固有信息损失**，不是实现 bug。`14_` 号 §5.7 的 `metal:'f0'` 选项（把 F0 当金属度近似）是唯一缓解手段。
- **互斥规则**：官方数据里有 **41,589 个像素金属度与 SSS 同时非零**，说明「互斥」是**渲染时取较大值**的规则，而非数据约束。`02_` 号文档的表述正确；转换器按 `metal > sss ? 清 sss : (sss > metal ? 清 metal : 都留)` 实现，相等时两者都保留，与该规则一致。SSS 通道 0.06% 的极端误差来自这组边界像素。

## 四、本轮发现并修复的两个真 bug

### 4.1 演示包被 canvas 预乘 alpha 破坏（严重）

**现象**：首轮端到端跑完后，报告显示 `lostF0Pixels=256 / lostPorosityPixels=0`，而按演示包源码常量应是 `512 / 512`。逐像素追查发现 `demo_metal_s.png` / `demo_stone_s.png` 解出来是 `(0,0,0,0)`，而非 `(210,231,20,0)` / `(30,20,30,0)`。

**根因**：`LabPBR2VV.html` 原 `makePNG()` 用 `canvas.toBlob()` 生成 PNG。canvas 对 `alpha=0` 的像素做预乘，**把 RGB 抹成 0**。而 LabPBR 的 `_s` 恰好用 alpha 存自发光，绝大多数像素 `alpha=0`，RGB 存的却是平滑度/F0/SSS 三个材质通道 —— 全部丢失。讽刺的是，原型里的 `decodePNG()` 特意自实现解码来绕开 canvas 预乘，但**生成演示包时又亲手踩了同一个坑**。

**影响**：真实用户上传的 LabPBR 包由 Photoshop / 材质工具导出，不经过 canvas，转换结果正确；但「一键生成演示包」是页面唯一的自测入口，金属块和石头会被转成「完全粗糙、非金属、不发光」，用户会误判转换器坏了。

**修复**：`LabPBR2VV.html:401` 起，新增 `encodePNGBytes()`，用 `CompressionStream('deflate')` 直接写 PNG 字节（IHDR/IDAT/IEND + CRC32，filter=none，color type 6），`makePNG()` 改为调用它，返回签名不变，所有调用点（演示包、`pack_icon`、缺色占位图）零改动。启动自检同时检测 `DecompressionStream('deflate-raw')` 与 `CompressionStream('deflate')`。

**修复前后对照**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `demo_metal_s` 首像素 | `(0,0,0,0)` | `(210,231,20,0)` |
| `demo_stone_s` 首像素 | `(0,0,0,0)` | `(30,20,30,0)` |
| `iron_block_mers` 首像素 | `(0,0,255,0)` | `(255,0,8,0)` |
| `lostF0Pixels` | 256 | **512** |
| `lostPorosityPixels` | 0 | **512** |
| D 组断言 | 2 项失败 | 全通过 |

### 4.2 报告少算自身

`REPORT` 在把 `_pbr2vv_report.json` 入包**之前**生成，`output.files` 记的是当时的 `E.length=14`，而最终 zip 有 15 个文件（UI 显示的也是 15），自相矛盾。修复：`LabPBR2VV.html` 在 push 报告 entry 后回填 `REPORT.output.files = E.length` 并重写该 entry 的字节，保证包内报告与实物完全一致。

## 七·补记二：alpha 非预乘结论 + Java 介绍同步（2026-11-15 深夜）

### 1）透明贴图的 RGB 丢失：不能靠「alpha 预乘」解决，本引擎也不需要它

用户问「带 alpha 的贴图 RGB 会丢失，解决方式是 alpha 预乘，需要做吗」。结论是**不需要，且预乘恰恰是要避免的**，理由：

- LabPBR 的 `_s` 把**材质数据放在 RGB**（R=感知平滑度 / G=F0 / B=孔隙率-SSS），**自发光放在 A**，绝大多数像素 `alpha=0`。
- 预乘的定义是 `RGB' = RGB × A / 255`。当 `A=0` 时 `RGB'` 被乘成 **0**，R/G/B 三个材质通道**彻底丢失**——这正是要防的那类丢失。
- 丢数据的元凶是 **canvas 的 `getImageData`/`toBlob`**：canvas 内部用预乘表示，`alpha=0` 区域的 RGB 读过/写出就被抹平。本引擎的 `decodePNG()` 与 `encodePNGBytes()` 从一开始就**绕开 canvas**，直接解 IHDR + IDAT + unfilter、用 `CompressionStream('deflate')` 直写字节，`ct===6` 时 `out[d..d+3]=cur[s..s+3]` 原样搬运四个通道，**零预乘、零信息损失**。
-  Canvas 只保留在**封面 JPEG 兜底解码**这一条路径上，而封面无 `alpha=0` 数据语义，安全。

新增 5 条真实浏览器断言（`alpha` 组）把这点钉死：构造 `alpha=0` 但 RGB 非零的像素 → `encodePNGBytes` 编码 → `decodePNG` 解码，逐字节验证 RGB 原样保留；并验证该像素仍能算出正确粗糙度（若被预乘抹成 0，粗糙度会变成 255）。这是本轮唯一与"预乘"有关的动作：**证明我们没有预乘，并锁死以后不会误引入**。

> 补充辨析：WebGL 纹理上传时的 `UNPACK_PREMULTIPLY_ALPHA_WEBGL` 预乘，解决的是**半透明边缘黑/白边**的渲染问题，属于"显示"阶段；本任务是**数据转换**（把 RGB 当材质数值读出重编码成 MERS TGA），二者语境不同，不能套用。

### 2）Java 包介绍同步到基岩版 + 转换记录

原先 `manifest.json` 的 `header.description` 硬编码为 `Converted from LabPBR by PBR2VV`，Java 源包 `pack.mcmeta` 的 `pack.description` 只取首行当包名、其余介绍全丢。本轮补齐：
