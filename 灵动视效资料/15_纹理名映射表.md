> 整理日期：2026-11-15　|　配套产物：`/workspace/LabPBR2VV/name_map.json`（478 条，2026-11-16 补录 33 条）
> 生成工具：`/workspace/LabPBR2VV/mapping/build_map.py`（原 `sync_assets.py` 已随 APK 工程移除）
> 依据：Mojang 官方 `bedrock-samples v1.26.70.23-preview-full.zip` 实物 + 社区纹理清单

## 一、为什么必须有这张表

原型的 `mapName()` 原本只查用户手填的 JSON，内置只有 2 条示例。实测下来这是最大的工程缺口：

| 指标 | 数值 |
|---|---|
| Java 1.21.x `textures/block/` 基名（清洗后） | **1083** |
| 官方样例包 `textures/blocks/*.texture_set.json` | **1315** |
| 两者**精确同名** | **612（56.5%）** |
| 需要改名或无法匹配 | **471** |

也就是说，不做映射直接按原名输出，**近一半方块的 PBR 材质会贴到不存在的纹理名上，被引擎静默忽略**。

顺带验证了上一轮的一个担心：旧教程里的 `oak_planks → planks_oak`、`light_gray_wool → wool_colored_silver`、`poppy → flower_rose` 并**没有过时**——这些旧式基岩名在 1.26.70 官方样例包里依然存在。所以「Java 1.13 扁平化名称 ↔ 基岩沿用旧名」仍是主要矛盾，不是版本漂移问题。

> **设计原则**：贴错材质比不映射更糟。所有自动推导的候选都必须满足「目标名在权威集合中存在」，宁可留原名让用户自定义。

## 三、命名差异的六类规则

生成脚本 `build_map.py` 把差异归纳为可解释的规则，而非相似度猜测。每条候选都要在目标集合里命中才收录。

### 3.1 目录映射（原型 `mapName` 已实现）

| Java | 基岩 |
|---|---|
| `assets/<ns>/textures/block/` | `textures/blocks/` |
| `assets/<ns>/textures/item/` | `textures/items/` |
| `assets/<ns>/textures/entity/` | `textures/entity/` |
| `assets/<ns>/textures/particle/` | `textures/particle/` |

### 3.2 颜色材质：前缀式 → 后缀式 / 旧基岩名（137 条）

| Java 形式 | 基岩形式 | 例 |
|---|---|---|
| `<c>_wool` | `wool_colored_<b>` | `black_wool → wool_colored_black` |
| `<c>_terracotta` | `hardened_clay_stained_<b>` | `black_terracotta → hardened_clay_stained_black` |
| `<c>_glazed_terracotta` | `glazed_terracotta_<b>` | `cyan_glazed_terracotta → glazed_terracotta_cyan` |
| `<c>_concrete` | `concrete_<b>` | `red_concrete → concrete_red` |
| `<c>_concrete_powder` | `concrete_powder_<b>` | — |
| `<c>_stained_glass` | `glass_<b>` | `blue_stained_glass → glass_blue` |
| `<c>_stained_glass_pane_top` | `glass_pane_top_<b>` | — |
| `<c>_shulker_box` | `shulker_top_<b>` | — |

**唯一颜色词替换**：`light_gray → silver`（其余 15 色同名）。注意 `<c>_terracotta` 与 `<c>_glazed_terracotta` 是**两个不同方块**，早期一轮模糊匹配把前者错配成了 `glazed_terracotta_black`，已按规则修正。

### 3.3 木材：`<wood>_X` → `X_<wood>`（41 条）

`oak / spruce / birch / jungle / acacia` 直接反转，但 **`dark_oak → big_oak`**（基岩沿用旧名）：

| Java | 基岩 |
|---|---|
| `dark_oak_planks` | `planks_big_oak` |
| `dark_oak_log` / `_top` | `log_big_oak` / `log_big_oak_top` |
| `dark_oak_leaves` | `leaves_big_oak` |
| `dark_oak_sapling` | `sapling_roofed_oak`（第三个旧名） |

### 3.4 门与生长阶段

- `<wood>_door_bottom → door_<wood>_lower`，`_top → _upper`（`oak` 的门用 `door_wood_lower/upper`）
- `stage0 → stage_0`：如 `beetroots_stage0 → beetroots_stage_0`、`carrots_stage3 → carrots_stage_3`

### 3.5 花与杂项显式对照（64 条）

从官方样例包的实际命名反查得到，逐条验证目标存在：

- 花：`allium→flower_allium`、`azure_bluet→flower_houstonia`（不是 `flower_azure_bluet`）、`poppy→flower_rose`、`dandelion→flower_dandelion`、`orange_tulip→flower_tulip_orange` 等
- 常用：`grass_block_side→grass_side`、`grass_block_top→grass_top`、`bricks→brick`、`cobweb→web`、`note_block→noteblock`、`powered_rail→rail_golden`、`andesite→stone_andesite`、`carved_pumpkin→pumpkin_face_off`

### 3.6 零歧义自动推导（203 条）

对规则未覆盖的名字，若其 **token 多重集**与某个基岩名完全一致（仅词序不同、允许 `light_gray↔silver`、`stage0↔stage_0`），且目标唯一，则自动收录。典型：

`acacia_boat → boat_acacia`、`allay_spawn_egg → spawn_egg_allay`、`baked_potato → potato_baked`、`chiseled_quartz_block → quartz_block_chiseled`、`packed_ice → ice_packed`。

这类推导**零歧义**（全流程 0 个多候选），比编辑距离/相似度匹配安全得多。

### 被主动剔除的 3 条

| Java 名 | 曾被误配为 | 剔除原因 |
|---|---|---|
| `chiseled_sandstone` | `sandstone_normal` | 雕纹砂岩 ≠ 普通砂岩侧面，官方包无对应名 |
| `chiseled_red_sandstone` | `red_sandstone_normal` | 同上 |
| `beehive_end` | `beehive_top` | 蜂箱端面 ≠ 顶面，语义存疑 |

这 3 条保持原名，交由用户在自定义映射里决定。

## 四、映射表结构

`name_map.json` 是纯 `{Java基名: 基岩基名}`，**只收录需要改名的 478 条**（精确同名不必列出），可直接整份粘贴进原型的「名称映射」输入框。

| 来源类别 | 条数 | 置信度 |
|---|---|---|
| `color` 颜色材质规则 | 137 | 高（结构性词表） |
| `wood` 木材规则 | 41 | 高 |
| `flower` 花显式表 | 8 | 高 |
| `misc` 其它显式对照 | 56 | 中（建议真机抽查，见 §七） |
| `auto-token` 零歧义推导 | 203 | 高（用词完全一致） |
| `manual-official` 官方实物补录 | 33 | 高（逐条在官方包实物中确认，见 20 号文档） |

质量校验结果：**478/478 的 key 都来自真实 Java 清单、478/478 的 value 都在权威目标集合（补录项经 `build_map.py` 逐条断言官方包存在）、无自映射冗余、无 value 重复**。完整元数据在 `mapping/name_map_meta.json`。

## 五、覆盖率

| 类别 | Java 基名 | 精确同名 | 规则/自动映射 | 未改名 | 覆盖率 |
|---|---:|---:|---:|---:|---:|
| `blocks` | 1083 | 612 | 268 | 203 | **81.3%** |
| `items` | 747 | 298 | 197 | 252 | **66.3%** |
| 合计 | 1830 | 910 | 478 | 455 | **75.8%** |

> 另有 13 条盔甲映射（`textures/models/armor/`）不在这两个清单内，单独计入上表「manual-official」。
> 2026-11-16 补录的 33 条来自用户实测反馈（末地框架 / 耕地 / 睡莲 / 旧版玫瑰 / 牡丹 / 大蕨 / 向日葵 / 丁香 / 全套盔甲），
> 成因与验证见 `20_未转换成功的成因与修复.md`。

「未改名」包含两种情形，引擎报告里明确区分说明：

- **精确同名**（正确的，无需处理）；
- **映射表未收录**（需要人工，或在 UI 自定义覆盖）。

转换报告的 `mapping` 字段给出 `builtinHits / customHits / unchanged`，`unmappedNames` 列出未改名条目（前 200 个）。完整未匹配清单在 `mapping/unresolved.json`（blocks 223、items 252）。

## 七、已知限制与下一步

1. **覆盖率 74%**：剩余 475 个未改名条目里，多数是 `anvil`、`brain_coral_*`、`*_particle`、`big_dripleaf_*`、`*_spawn_egg` 之外的杂项，以及 Java 独有的物品图标。它们保持原名，不会贴错，但也不会生效。
2. **key 不含目录**：`mapName` 用基名查表，若 `block/` 与 `item/` 出现同名却需不同映射会冲突。本次生成时检测到 **0 冲突**；未来加表需用 `block/<name>` 形式的带目录 key 并改引擎。
3. **`entity/` 完全未处理**：官方样例包有 851 个 entity texture_set，命名体系（如 `entity/chest/normal`）与 Java 差异更大，且 LabPBR 材质包里 entity 贴图占比小，留作二期。
4. **1.13 之前的旧包**：1.12.2 / 1.8.9 用 `textures/blocks/` 复数目录 + 数字 ID 名，需先做扁平化。`mapping/oneTwelveTwo.js`、`oneEightNine.js` 已备好清单，可做一条旧版预处理链。
5. **56 条 `misc` 显式对照**建议在真机抽查（尤其 `polished_* → stone_*_smooth`、`cut_sandstone → sandstone_smooth`、`tall_grass / sunflower` 等双高植物），它们目标名存在但语义对应未逐条比对。
6. 未匹配项最实用的补法：在 UI 里填 `{"java_name":"bedrock_name"}` 自定义覆盖，优先级高于内置表；批量补充后也可回写进 `build_map.py` 的 `MISC` 重新生成。
