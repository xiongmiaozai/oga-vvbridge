## 二、三道关卡

### 1) 名字关卡：Java 与基岩不是同一套命名

Java 1.14 起改过一轮方块名，基岩却长期保留旧学名/旧习惯，于是出现系统性错位：

| 语义 | Java | 基岩 | 错位原因 |
|---|---|---|---|
| 牡丹 | `peony` | `paeonia` | 基岩用拉丁属名 |
| 丁香 | `lilac` | `syringa` | 同上 |
| 垂泪藤/高蕨/高草 | `large_fern` / `tall_grass` | `double_plant_fern` / `double_plant_grass` | 基岩按"双格植物"归类 |
| 耕地 | `farmland` / `farmland_moist` | `farmland_dry` / `farmland_wet` | 干湿用词不同 |
| 睡莲 | `lily_pad` | `waterlily` | 词序不同 |
| 末地框架 | `end_portal_frame_*` | `endframe_*` | 基岩缩写 |
| 盔甲 | `diamond_layer_1` | `diamond_1` | 基岩不分 layer 前缀 |

这些名字在 445 条旧表里**一条都没有**——映射表当时以"自动规则 + 官方 texture_set 交集"生成，规则拿不准的一律留空（宁可留空也不猜）。本次按官方实物逐条补录，见 §三.2。

### 2) 目录关卡：`mapName()` 把未知目录一律塞进 `blocks/`

旧实现的目录推断只认四种情况，其余全部兜底成 `blocks`：

```js
if (lower.includes('/textures/item/')) dir = 'items';
else if (lower.includes('/textures/entity/')) dir = 'entity';
else if (lower.includes('/textures/particle')) dir = 'particle';
else if (lower.includes('/textures/block/')) dir = 'blocks';   // ← 其余默认 blocks
```

于是 Java 的 `assets/minecraft/textures/models/armor/diamond_layer_1.png` 被写成
`textures/blocks/diamond_layer_1.png`——**目录和名字double 错**，基岩永远读不到。地图同理进了 `blocks/`。

修复：改为**沿用 Java 原目录**，只做两处改写（`block→blocks`、`item→items`），并新增 `PBR_DIRS` 白名单。

### 3) 格式关卡：`.tga` 会压过 `.png`

这是矮蕨/高蕨/丁香"名字明明对了却仍不生效"的真正原因。Mojang 官方 **Texture Sets 文档**原文：

> The priority of file extensions, in case you have duplicate image references, is: `.tga` > `.png` > `.jpg` > `.jpeg`.
> For example: if `grass.png` and `grass.tga` both exist in the folder, `grass.tga` will be chosen.

官方包对 **50 个方块基色只提供 `.tga`**（不是 png），包括：

```
leaves_oak / leaves_birch / leaves_spruce / leaves_jungle / leaves_acacia / leaves_big_oak
mangrove_leaves / pale_oak_leaves / grass_side / fern / fern_carried / reeds
double_plant_fern_top|bottom / double_plant_grass_top|bottom / double_plant_syringa_top|bottom
cactus_top|side|bottom / kelp_* / scaffolding_* / seagrass_doubletall_* / grindstone_*
```

我们写 `fern.png`，官方自带 `fern.tga` → 引擎按优先级选 tga → **我们的图被静默丢弃**，表现就是"没转换成功"（连报错都没有）。

修复：内置 `TGA_BASE` 名单（上表 50 项），命中时把基色**重编码为 32-bit BGRA TGA** 输出。往返无损、alpha 原样保留（实测 `alpha=100` 输出仍为 `100`，未预乘）。

> **订正 `18_` 号文档的说法**：当时结论是"树叶不需要特殊处理，基色原样复制即可"。
> 就 PBR 通道而言没错（MERS/法线照常生成），但**格式层面必须跟 tga**，否则整组贴图被压制。
> 树叶类（`leaves_*`）与 `grass_side` 早就在这个坑里。

### 4) 基岩不参与 PBR 的：地图

`textures/map/map_background.png` 在基岩里**路径同名、可以覆盖**，但官方**没有** `map_background.texture_set.json`——地图渲染不走 PBR 管线，写 MERS 也不会被用。同理 `textures/ui/`、`font/`、`gui/`、`painting/`。

旧实现把它们硬塞进 `blocks/`（错目录 + 无效 MERS）。现在改为**跳过**并在报告里计数 `skippedNonPBRDir`，不再产出垃圾文件。

## 五、还剩什么

- **绯红/诡异木板本来就能转**：实测输出 `crimson_planks.png` + `_mers.tga` + `.texture_set.json` 三件齐全、目标名完全一致。若你在游戏里仍看不到效果，优先排查：① 是否与 ENRO 等包叠加且它在上层（同名 texture_set **不合并**，上层整体覆盖）；② 是否开了"叠加模式"导致回退缺失；③ 换包后是否重启世界/清缓存。
- **地图/UI/字体/画**：基岩不支持，已跳过。想改它们的观感只能走 `textures/map/` 原名替换（无 PBR），或改 UI 资源。
- **盔甲**：名字与目录已修，但 Java 是"分层双图"、基岩是"单位置双图 + 幼年 `*_baby`"，**UV 布局不一致**时贴图会错位；幼年盔甲（`*_baby`）Java 端没有对应文件，覆盖不到。
- **动画贴图**：`.mcmeta` 与基岩 `flipbook_texture.json` 机制不同，仍未支持（沿用 `16_` 号结论）。
- 新版本新增的双格植物/花（如 1.21 的 eyeblossom）仍需按同样方式补 `double_plant_*` 映射。

## 六、二次实证：用用户真包 `ENRO 0.20.2 主体 128x` 跑完整转换

前五节用的是「按名字造包」。2026-11-16 拿到用户实际在用的 Java 源包（38 MB / 1494 文件 / `pack_format 15`）后，用同一套真实 Chromium 流程复跑，结论有一处**重要订正**。

### 1) 源包画像

| 项 | 实测值 |
|---|---|
| `pack.mcmeta` | `pack_format 15`、`supported_formats [15,255]`、介绍「层级:1 / 纯修改贴图实现，适配性较高」 |
| 结构 | `assets/minecraft/textures/` 1455 个：`block/` 1235、`entity/` 131、`painting/` 37、`item/` 25、`particle/` 15、`gui/` 4、`colormap/` 4、`map/` 3 |
| 分组 | **515 组**，其中 **466 组有 `_s`**、**424 组有 `_n`** |
| 扩展名 | 全 png，无 tga/jpg |
| 附带 | `optifine/{color,emissive,texture}.properties`（OptiFine CTM/自发光，基岩不认） |

### 2) 盔甲的真相（订正 §二.2）

前面把盔甲归因成「被兜底塞进 `blocks/`」。真包一到，发现还有更深一层：**Java 1.21.2+ 换掉了盔甲的存放路径**。

| Java 旧路径（≤1.21.1） | Java 新路径（1.21.2+，本包） | 基岩目标 |
|---|---|---|
| `textures/models/armor/diamond_layer_1.png` | `textures/entity/equipment/humanoid/diamond.png` | `textures/models/armor/diamond_1.png` |
| `…_layer_2.png` | `textures/entity/equipment/humanoid_leggings/diamond.png` | `…/diamond_2.png` |
| 无 | `textures/entity/equipment/humanoid_baby/diamond.png` | `…/diamond_baby.png` |

所以本包**根本没有 `models/armor` 目录**——第一遍按 `armor` 关键字搜不到，容易误判成「源包没带盔甲」。实际它带了 **26 组**（humanoid 9 + leggings 8 + baby 9），全在 `entity/equipment/` 下。

而 `PBR_DIRS` 当初是**精确集合** `{blocks,items,entity,particle,models/armor}`，`entity/equipment/humanoid` 不等于 `entity` → 26 组全部命中「非 PBR 目录跳过」。这才是「所有盔甲全套没转换成功」的真正原因。

**修复**：
- `isPBRDir()` 改前缀判定，`entity/**` 一律放行（官方包实测 851 个 `entity/*.texture_set.json`，床/猫/狼/鞍具都吃 PBR）；
- 新增 `ARMOR_DIRS` 表，把三个新目录映射到 `models/armor/{mat}_{1|2|baby}`，材质名按基岩改写：`chainmail→chain`（幼年却是 `chainmail_baby`）、`turtle_scute→turtle`（幼年回 `turtle_scute_baby`）、`copper/gold/iron/diamond/netherite/leather` 同名；
- `leather_overlay`（Java 的染色叠加层）基岩无对应文件，标记跳过并计 `skippedArmorLayer`；
- 基岩皮革三件是 **`.tga` 基色**（`leather_1/2/baby`），加入 `TGA_BASE`，否则会被官方 tga 压制。

### 3) 床：同名，只有浅灰叫法不同

`textures/entity/bed/{color}.png` 两边路径与命名完全一致（15 色），唯一差异是 Java `light_gray` ↔ 基岩 `silver`。加一条目录内特例即可，16 组全部转出。

### 4) 修复前后对比（同一份真包，真实转换）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 成功转换组数 | 412 | **451** |
| 非 PBR 目录跳过 | 63 | **21** |
| 输出文件数 | 1282 | **1399** |
| 盔甲输出 | 0 | **69 个文件**（23 组 × 基色 + MERS + texture_set） |
| 床输出 | 0 | **48 个文件**（16 色） |
| 按 tga 输出的基色 | 18 | 21（+3 皮革盔甲） |
| 盔甲无对应层跳过 | — | 3（`leather_overlay`） |

剩余 21 组跳过全是「基岩端确实不该写 MERS」的：`painting` 12、`colormap` 3、`gui/title` 2、`map` 2、`item/icon` 2。其中**画**值得单独说明：基岩 `textures/painting/` 确实有 `texture_set.json`，但 1.21 换过画名（Java `alban/bomb/kebab/plant…` ↔ 基岩 `baroque/passage/endboss/bouquet…`），两套名字交集只有 2 个，需要另一张映射表，暂未做。

### 5) 两个必须提醒的默认项

- **法线默认是关的**：源包 424 组 `_n` 默认全部不输出（`emitNormal:false`，依据是官方包几乎不用法线、且要重建 Z 并丢 AO/高度）。要法线细节，转换时手动勾「输出法线贴图」。
- **OptiFine 配置无效**：包的 `optifine/*.properties`（CTM 连接纹理、自发光）属 OptiFine 私有机制，基岩没有对应实现，转换器不读取也不输出。这部分视觉差异无法通过转换保留。
